# Maigret：我们的完整理解

> 研究日期：2026-09-10。源码基准：`578d603e8f1dd594b3e9295857dacc41e9a66595`，代码版本 0.6.5。本文整合本次对话中的问题与结论；文档与关键源码核对已完成，未安装或运行上游扫描。使用价值与扩展优先级是研究判断，效果未实测。

## 1. 一句话定位

**Maigret 把很多网站的账号检查规则汇集起来，让用户输入一个在网站上设置的账号用户名后，自动检查这些网站上的同名公开账号，再整理资料与关联链接。它不是按实名查人的搜索工具。**

它首先回答“规则库覆盖且本次选中的哪些网站上，能找到这个账号用户名”，而不是直接回答“某个人注册过哪些网站”。

这里的用户名是 username / handle，例如主页地址中的 `bluecat123`，需要与显示昵称和实名区分：

| 名称 | 含义 | 与搜索的关系 |
| :--- | :--- | :--- |
| 账号用户名 | 用户在网站设置的账号标识，如 `bluecat123` | 主要查询输入；按各站点规则检查同名账号 |
| 显示昵称 | 主页上显示的名字，可与用户名不同或重复 | 不能假设任意显示昵称都能用于地址检查 |
| 实名 | 现实身份中的姓名 | 不会自动由实名推断出其全部用户名或注册账号 |
| 平台 ID | 平台分配的标识符，可能是数字 | 部分检查支持，但需匹配对应标识符类型 |

如果有人恰好把自己的姓名设置为账号用户名，程序仍然只是按这个字符串检查账号，不是在验证实名。搜索后可能提取主页上公开的姓名字段，这与“按实名定位账号”也是两回事。上述区分依据项目的用户名／ID 输入和地址规则机制。[输入与筛选说明][S8]、[检查源码][S3]

## 2. 它提前收集了什么？

我们逐步确认：开发者和社区贡献者收集、适配网站，再交给统一程序执行检查。维护内容主要包括：

| 维护对象 | 作用 | 示例或说明 |
| :--- | :--- | :--- |
| 网站与地址模板 | 知道去哪里检查 | `https://github.com/{username}` |
| 标识符与格式规则 | 判断输入适用于哪些站点 | 用户名、部分平台 ID；不支持的格式可跳过 |
| 请求参数 | 适应站点的主页或接口 | GET / HEAD / POST、请求头或载荷 |
| 账号判断规则 | 区分存在、未找到与错误 | 页面文字特征、状态码、重定向相关行为 |
| 标签、排名、禁用状态 | 选择本次检查范围 | 国家、类别、流量排名、失效规则 |
| 已存在与不存在的样本 | 自检规则是否仍然有效 | `usernameClaimed` / `usernameUnclaimed` |

**这里的数据库是“网站规则数据库”，不是提前收集好的“所有网站用户数据库”。** 查询时程序再访问对应网页或接口。规则可以复用，项目也提供自检与辅助维护能力，不能理解成每一条规则都只能从零手写。[站点名单][S2]、[检查源码][S3]、[功能文档][S6]

## 3. 查询时具体发生什么？

假设输入虚构用户名 `bluecat123`，典型流程如下。示例只是说明机制，未访问对应账号地址。

1. **选择网站。** 根据标签、排名、禁用状态、输入标识符类型等确定目标范围。
2. **构造请求。** 用用户名替换站点地址模板，例如 `https://github.com/bluecat123`；必要时使用检查接口。
3. **并发访问。** 通过异步任务队列同时等待多个网站响应，设置并发上限、超时与重试。
4. **按站点规则判断。** 得到账号存在、未找到或无法判断等结果。
5. **提取公开资料。** 在支持的页面中解析昵称、简介、位置、头像链接、其他账号链接等，提取范围因站点而异。
6. **继续关联与输出。** 从提取字段和链接中发现新的用户名或平台 ID，继续搜索；最终生成报告或关系图。[检查源码][S3]、[任务队列][S4]、[递归入口][S5]

### 结果如何判断？

| 方式 | 判定依据 | 典型局限 |
| :--- | :--- | :--- |
| `message` | 命中存在特征，且未命中不存在特征 | 网站改版、语言变化或弱特征可能引起误判 |
| `status_code` | HTTP 响应是否为 2xx | 不存在页面也可能返回 200 |
| `response_url` | 关闭重定向后，检查 2xx 和存在特征 | 不同站点的跳转行为需要单独适配 |

源码先识别部分错误页面；检测到访问错误时可标为 `UNKNOWN`。`message` 模式未配置存在特征时有默认存在逻辑，因此并不是所有规则都有强正面证据。验证码、限制访问或连接超时，也可能导致无法可靠判断。[结果判定源码][S3]

核心检测是规则驱动的自动化检查。AI 摘要是后续可选环节：把已生成的报告发给兼容接口的大模型进行概括，不会因此让原始身份关联自动变得可靠。[AI 模块][S7]

## 4. 会查哪些网站？

**范围由规则库与本次筛选共同决定，不是自动遍历整个互联网。** 官方 README 概括为支持 3,000+ 站点；固定提交的 `sites.md` 列表标题统计为 5,373 条站点／搜索方法。两者是不同粒度的介绍，应理解为规则覆盖规模。同一平台可有多种检查方法，列表还包含禁用条目，不能等同于 5,373 个独立、实时可用网站。[固定 README][S1]、[固定站点名单][S2]

名单中的代表性条目如下，收录不表示本次已经验证可用：

| 类别 | 代表性条目 |
| :--- | :--- |
| 技术社区 | GitHub、CSDN、V2EX |
| 社交与讨论 | Reddit、Instagram、Twitter、Telegram |
| 视频平台 | YouTube、TikTok、Bilibili |
| 中文社区 | 微博、知乎、豆瓣 |
| 图片与音乐 | Pinterest、Flickr、SoundCloud |
| 游戏 | Steam，以及按 ID 等不同检查方法 |

默认按流量排名选取约前 500 个站点，相关镜像可能额外加入；`-a` 扩大到全部符合筛选条件的条目，禁用条目默认仍跳过。可指定网站或按类别、国家标签筛选。Bilibili 等部分检查需要对应平台 ID，显示昵称不一定能直接拿来检查。[筛选与标识符选项][S8]

完整名单：[固定版本 sites.md][S2]。具体可用性取决于请求环境、站点限制及规则有效性，本文未进行跨站实测。

## 5. 它具体提供什么能力？

| 能力 | 用户得到什么 | 边界 |
| :--- | :--- | :--- |
| 批量账号发现 | 哪些站点可能存在相同用户名 | 不证明账号归属同一个人 |
| 公开资料提取 | 支持的主页字段和关联链接 | 每个站点字段完整度不同 |
| 递归搜索 | 从发现的其他用户名或 ID 继续找 | 无关线索可能扩散，需复核 |
| 报告和图谱 | HTML、PDF、JSON、CSV 等；Web 界面、交互图、Neo4j 导出 | 图中关联不自动确证身份 |
| Python 集成 | 在自己的程序里调用异步搜索 | 服务化仍需考虑任务管理、资源与限速 |
| 可选 AI 摘要 | 对已有报告进行概括 | 需要额外配置；事实与推断须分别核验 |

普通搜索不要求用户提供 API Key；AI 模式需要单独配置兼容服务。项目支持部分代理与访问错误处理，但没有保证所有验证码或反自动化限制都能解决。[README][S1]、[功能说明][S6]、[AI 模块][S7]、[库使用][S9]

它不是直接按邮箱反查注册账号的工具，也不等于平台内容采集器。例如官方 FAQ 说明，Telegram 检查不包含频道帖子、成员或消息内容。主页中提取到公开邮箱，与输入邮箱查询哪些网站注册过，是不同能力。[官方 FAQ][S10]

## 6. 直接网页搜索不就可以了吗？

可以，少数网站上的简单查询通常适合直接搜索。Maigret 的增量价值在跨站批量检查与整理。

| 方式 | 依赖什么 | 优点 | 容易遗漏什么 |
| :--- | :--- | :--- | :--- |
| 搜索引擎搜用户名 | 搜索引擎已收录的网页 | 范围广，可发现规则库之外的网页与内容 | 未收录、排名靠后的个人主页 |
| 人工去网站搜索 | 站内搜索、人工浏览与判断 | 可结合上下文、处理复杂页面 | 大规模查询耗时，容易漏记 |
| Maigret 批量检查 | 站点规则、可访问的主页或接口 | 自动检查、提取、递归、统一报告 | 未适配网站、失效规则、受限页面 |

例如某小论坛的主页没有被 Google 收录，只要论坛在规则库里、主页可访问且规则有效，Maigret 就有机会直接检查到。反过来，搜索引擎也可能找到 Maigret 没适配的网站。这个比较是基于两种机制的推论，本文没有测量新增发现率或耗时差异。

**它自动化了原本可人工执行的一批步骤，不能理解成一定比网页搜索更完整、更准确。**

## 7. 所以它主要是“体力活”吗？

我们的理解是：**大量价值确实来自网站收集、逐站适配与长期维护，同时需要把规则组织成可靠的批量检查程序。**

- 人工维护：找到正确入口、比较存在与不存在页面、配置规则、应对改版与失效。
- 工程实现：规则复用、异步并发、超时重试、错误识别、字段提取、递归与报告。
- 长期难点：网站越多，越要持续核对实际成功率、误报和失效情况。

从本次研究看，它主要是实用的工程整合项目。单个站点的检测可以很简单；让大量站点长期稳定、查得准，是更难的维护问题。是否值得使用，应看它节省多少操作、有效覆盖多少目标网站，而不只看站点总数。

这属于基于源码组织和检测机制的研究判断，不是对维护工作量或算法创新程度进行过量化评测。

## 8. 使用场景与明确边界

适合的使用场景：

- 自查自己的公开数字足迹，找回遗忘账号或检查关联信息。
- 在授权范围内盘点账号及公开资料。
- 查找品牌同名账号、疑似冒充候选，再人工核对。
- 对已知公开主页进行资料研究，整理相关账号与来源。
- 将账号发现作为已有分析系统的一环。

解释结果时保留三个区分：

1. **查询用户设置的账号用户名，不是按实名查人；同名账号存在 ≠ 属于同一个人。**
2. **没有查到 ≠ 一定没有注册。**
3. **站点条目很多 ≠ 当前每个站点都有效。**

## 9. 哪些扩展更有价值？

以下为建议，并非声称上游当前已完整具备这些产品能力。

| 优先方向 | 可扩展内容 | 解决的问题 |
| :--- | :--- | :--- |
| 账号核验 | 主页互链、共同官网、简介一致性、人工确认与排除 | 减少同名误合并 |
| 规则质量管理 | 基于已有自检增加趋势记录、多语言样本、误报反馈和回归检查 | 将名义覆盖转成实际可用覆盖 |
| 证据追溯 | 记录 URL、采集时间、命中特征、规则版本、必要页面证据 | 解释为什么产生这条结果 |
| 增量监测 | 对自有或授权账号定期比较新增账号、简介与链接变化 | 减少重复全量阅读 |
| 服务化 | 任务队列、缓存、按域名限速、取消任务、结构化 API | 支持稳定集成与多人使用 |
| AI 证据约束 | 摘要引用来源，标记事实、推断、冲突和未知 | 改善已有 AI 输出的可复核性 |

如果做二次开发，我们倾向于先提升核验、追溯和规则质量，再扩张数量。Web 界面、报告和可选 AI 已经存在，不能把简单增加一个界面或摘要当作从零补齐核心能力。[现有功能][S6]

## 10. 验证范围与复现入口

已核对：上游提交、版本文件、MIT 许可证、站点名单；`checking.py` 的结果判定与资料提取；`executors.py` 的队列调度；`maigret.py` 的关联标识符提取与递归；`ai.py` 的报告发送逻辑。

未验证：实际站点访问、扫描准确率、实时覆盖、速度、递归质量、上游报告输出与 AI 摘要质量。本次没有复制完整上游仓库、安装其运行依赖或部署上游账号搜索服务；研究网页仅静态展示本文与总览图。

如后续体验，可参考官方命令。下列是未执行示例，安装得到的版本不保证等于本研究提交：

```powershell
pip install maigret
maigret YOUR_USERNAME --site GitHub --no-recursion --html
maigret YOUR_USERNAME --html
```

严格复现源码研究应检出本文固定提交，并按该提交 README 安装。验证时先用少数已知存在和不存在的账号校准，再扩大范围；将错误与未找到分别记录。
