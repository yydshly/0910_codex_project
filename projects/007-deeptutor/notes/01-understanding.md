# DeepTutor：通用 AI 能力之上的教学流程

研究日期：2026-09-10。DeepTutor 基线为 v1.6.6，提交 `7a96bba1ae03401644c17763a2411c28aff3dcc9`。本文依据官方说明、核心源码和本次讨论整理；未部署上游，未测量真实模型质量、费用或教学效果。

[完整架构图（SVG，可放大）](../assets/full-architecture.svg) · [高清图片（PNG）](../assets/full-architecture.png)。按“输入与产物 → 教学闭环 → 运行与知识层 → 基础模型 → 产品对照 → 扩展与边界”阅读。图是职责与信息流的概念架构，不是独立服务的部署拓扑。

## 1. 我们最终形成的理解

**DeepTutor 的底层与许多 AI 知识库产品相似，其特色主要在上层教学业务逻辑，以及把通用 AI 能力组织成可持续的学习过程。**

- **库的能力：** 接入资料和现成模型，提供问答、分步解题、出题练习、阅读研究、学习路径与复习，保存作答和学习状态。
- **与其他产品比较：** NotebookLM 提供资料学习成品，Open Notebook 偏笔记与资料研究，SurfSense 偏多来源研究、连接器与协作；DeepTutor 更着重可修改的教学流程。能力有重叠，底层方法有共性，工程实现和业务规则仍有实质差异。
- **对我们的意义：** 已有 SurfSense 研究帮助我们理解资料接入与检索；进一步借鉴 DeepTutor 的教学状态和工具反馈，探索“项目讲解 → 可执行练习 → 结果验证 → 学习反馈”的开源项目导师。这是扩展建议，尚未实现。

它是带网页界面的开源应用，可以自行部署和修改。使用者提供资料与目标后，可以问答、解题、练习、阅读、研究并保存学习记录。它接入模型、检索和工具服务，核心价值在于这些能力怎样被调度和约束。[项目说明][S1]

这个理解不等于“只有界面和提示词”。DeepTutor 也包含资料检索、上下文、记忆、工具执行与运行机制等工程工作。更准确的研究角度是：共用哪些基础能力，新增哪些数据、规则与执行流程。

## 2. 从使用者角度看，它能做什么

| 能力 | 用户可以提出的任务 | 系统承担的工作 |
| :--- | :--- | :--- |
| 资料问答 | 根据教材解释一个概念 | 找到资料、组织解释、关联来源 |
| 解题 | 分步骤完成题目并检查结果 | 制定计划、调用工具、逐步推进 |
| 出题练习 | 根据第三章生成练习 | 组织题目、答案及相应检查流程 |
| 学习路径 | 从基础学到理解特征值 | 拆分知识点、记录作答、检查掌握门槛、安排复习 |
| 阅读与视频学习 | 解释这一页或这一段字幕 | 绑定材料位置及来源上下文 |
| 研究与可视化 | 比较方法并解释差别 | 分解主题、检索、汇总、生成图表或其他表达 |
| 知识沉淀 | 把学习结果保存下来 | 笔记、题库、互动书、写作与记忆管理 |

这些能力来自官方产品说明；具体可用范围取决于模型、服务和可选依赖配置。[功能说明][S2] [学习路径][S3] [阅读][S4]

以《线性代数》为例，一条典型路径可以是“矩阵运算 → 线性变换 → 特征值 → 练习 → 达到门槛后继续 → 到期复习”。这是根据产品机制构造的示例，不是本次实际运行结果。

## 3. 三层技术：底座、工程、教学业务

| 层次 | 负责什么 | DeepTutor 的作用 |
| :--- | :--- | :--- |
| 基础 AI 能力 | 理解与生成、Embedding、语音或视觉等 | 接入现成模型；接入能力不等于所有功能默认可用 |
| 通用 AI 工程 | 解析、检索、上下文管理、工具调用、会话与记忆 | 集成能力，管理执行和信息流 |
| 教学业务逻辑 | 学什么、怎么教、怎么考、何时继续与复习 | 保存学习状态，实施流程与规则 |

“学完一章才能进入下一章”说明了职责边界：模型生成讲解、题目并可辅助判断回答；程序保存作答记录、计算掌握度、检查通过条件和开放下一步。

当前基础掌握度代码使用最近最多五次作答的加权正确率。只有一次作答记录时上限为 0.5，两次时上限为 0.8，避免一次偶然答对就得到高掌握度。这是明确的程序规则，也说明当前基础算法较简单，不能据此认为系统已精确理解学习者的真实能力。[评分源码][S5]

当前版本以共享智能体循环和能力接口组织运行：模型决定是否调用工具，工具结果进入上下文，再继续生成。Solve 在循环上加入计划、完成步骤和有限重规划；Research 则有澄清、拆分、分块研究和报告流程。不同能力共享基础，同时保留专门的循环或流水线。[循环扩展][S6] [Solve][S7] [Research][S8]

记忆是另一项工程能力：L1 对应工作区实体与变化，L2 提取各类活动摘要，L3 汇总跨活动信息及偏好。它使上下文可以持续复用，不等于每次学习都重新训练模型参数。记忆引用的精确程度有差别，也不能一概视为完整、逐条可追溯的事实链。[记忆文档][S9]

资料读取不只有一条向量检索路径。默认 LlamaIndex 使用向量与 BM25 融合；可选图检索集成；PageIndex 沿文档树寻找页面，不要求向量索引；沉浸式阅读可以按页或章节直接读取。现有远端知识库与 Obsidian 等实时资料有不同访问方式。每个知识库的集成决定索引和查询方式，图中列出的能力不表示同时启用。[检索集成][S20] [阅读方式][S4]

## 4. 与 NotebookLM 的关系

**资料问答、总结、出题和解释错误答案本身不是 DeepTutor 独有的能力。** NotebookLM 已提供来源问答、学习卡片、测验及音视频概览。[Google 学习功能][S10]

| 维度 | NotebookLM | DeepTutor |
| :--- | :--- | :--- |
| 使用方式 | 使用 Google 提供的在线产品 | 安装开源应用并配置相关服务 |
| 资料学习 | 问答、总结、卡片和测验等 | 有大量重叠能力，并组织专门学习路径 |
| 流程控制 | 在产品提供的功能内使用，也能配合 Gemini 学习功能 | 可修改知识点推进、评分、工具和教学规则 |
| 模型与工具 | 使用 Google 提供的能力 | 可选择模型与检索集成，连接外部工具 |
| 维护责任 | 服务商维护产品 | 自行维护部署、配置与版本 |

截至研究日期，Google 已于 2026-07-16 宣布将 NotebookLM 更名为 Gemini Notebook，并开始提供原生代码执行；开放情况取决于账户。本文沿用熟悉的 NotebookLM 名称。因此，不能把“NotebookLM 只能总结、不能出题或执行代码”当作比较前提。[官方更新][S11]

Gemini 的学习笔记本也会根据目标、资料和诊断测验组织小课与练习。教学功能存在竞争和重叠；DeepTutor 更明确的差异是可自行部署、检查源码和修改流程，而不是已证明教学效果更好。[Gemini 学习说明][S12]

## 5. Open Notebook 与 SurfSense：高度重叠的同类项目

我们此前研究 SurfSense 的“资料接入 → 解析切分 → Embedding 与全文检索 → 证据组装 → 模型生成”，可以直接用于理解 Open Notebook 的大部分基础概念。[SurfSense 固定版本][S13]

| 维度 | Open Notebook | SurfSense |
| :--- | :--- | :--- |
| 组织方式 | 围绕笔记本管理资料、笔记、对话和成果 | 围绕工作区管理资料、研究、连接器与协作 |
| 共同能力 | 多模型、自部署、资料导入、搜索问答、引用与播客 | 同样具备这些基础能力 |
| 当前侧重点 | 资料研究、上下文选择、内容转换、笔记与播客 | 多来源研究、实时平台数据、工具连接与自动化 |
| 存储与组件 | SurrealDB，Python / FastAPI，Next.js | PostgreSQL / pgvector，Redis 与后台任务等 |
| 研究价值 | 如何组织一组材料并形成可复用笔记与内容 | 如何接入、同步、检索多来源信息并推动任务 |

这是侧重点而非互斥边界。Open Notebook 也有 API 与可编排流程；SurfSense 也能用于研究几份 PDF。两者的实际质量不能只靠架构或功能清单判断。[Open Notebook 架构][S14] [SurfSense 说明][S13]

“给十份项目文档做比较和笔记”属于两者重叠范围；“结合实时社区信息持续更新研究并让同事参与”更贴近 SurfSense 当前强调的连接器、自动化和协作方向。具体数据源与任务仍需配置验证。

检索源码提供了一个实质差异：Open Notebook 的 Ask 路径先制定搜索策略，再分路向量检索、生成局部答案并汇总；SurfSense 已研究的混合检索路径融合向量和 PostgreSQL 全文排名，再按文档组织片段。这里是不同范围的代码路径对照，不是对两个系统全部检索方式的穷举。[Open Notebook Ask][S15] [SurfSense 混合检索][S16]

SurfSense 该路径使用 PostgreSQL 全文排序，不应直接称为 BM25。Open Notebook 支持全文搜索，也不能因为 Ask 这条路径用了向量搜索，就推断整个产品不支持全文检索。

## 6. “底层类似”成立到什么程度

| 观察层次 | 我们的判断 | 不能直接推出什么 |
| :--- | :--- | :--- |
| 基础模型 | 很多产品调用现成的生成、向量或语音模型 | 不代表模型版本、训练方式、能力与配置完全相同 |
| 通用方法 | 解析、检索、提示词、工具与工作流有强共性 | 不代表检索路径、证据质量和成本相同 |
| 系统架构 | 常见前端、后端、存储、任务与模型服务 | 不代表权限、调度、恢复和状态管理相同 |
| 业务规则 | 围绕研究、教学或复习形成不同数据与流程 | 不能把所有业务增量都解释成界面变化 |
| 展示层 | 摘要、卡片、表格的一些变化确实较浅 | 不能据功能名称多少推断技术突破多少 |

同一资料、同一模型，把“生成摘要”改成“生成十张卡片”，有时主要是提示词、输出格式和渲染的调整。但增加每日复习调度、保存作答历史、更新掌握度，就需要额外的数据结构和程序逻辑。

检索也会影响真实结果：关键证据没有被找到，生成模型可能缺少回答依据；材料解析错误、旧版本混入上下文或权限过滤失败，都不是界面差异。这些是工程上的因果分析，不是本次实测结果。

使用同一框架不代表执行过程相同。开源产品也未必提出了新的模型算法；其价值可以来自成熟组件的组合、流程实现与维护质量。商业产品未公开的内部实现，应明确保留未知。

| 产品 | 重点职责 | 对我们的参考价值 |
| :--- | :--- | :--- |

## 8. 对我们的研究与扩展意味着什么

**先掌握一套通用底座，再检查每个项目实际新增了哪些数据、规则和执行步骤。** 已经理解 SurfSense 后，不必把 DeepTutor 的资料问答重新当成一套陌生技术。

- 先看教学状态：知识点、作答记录、当前目标如何保存，如何决定下一步。
- 再看评分与复习：规则是否足以表达目标，何时可以更换更可靠的评估方法。
- 再看工具闭环：题目能否通过代码、数学验证器或实践环境得到可检查的反馈。
- 最后看效果：资料能否正确解析，证据是否完整，判题是否可靠，成本与延迟是否可接受。

适合我们尝试的方向是“开源项目学习导师”：读取一个仓库的文档和关键代码，讲解架构，给出可执行练习，再根据执行结果反馈。资料接入、讲解、练习与评估需要连接成实际流程。这是后续建议，本子项目没有实现该教学系统。

其他可扩展方向包括垂直学科资料与专家题库、教师班级工作流、企业培训和学习效果评测。优先验证一个小流程，避免先堆积大量相似功能。

## 9. 能力、结论与验证边界

- **已核对：** 官方功能说明及部分源码路径，包括循环扩展、解题、研究、基础评分、Open Notebook Ask 和 SurfSense 混合检索。
- **我们的理解：** 三层职责划分、产品侧重点、不同工程实现可能影响质量及扩展优先级。
- **未验证：** 上游部署、实际问答与判题、掌握度有效性、长期学习收益、多用户安全性、检索性能、真实费用。
- **网页范围：** 静态阅读展示，同一份 Markdown 在构建时生成 HTML，不调用模型或学习服务。
- **部署边界：** 本地文件可运行不等于网页已上线；只有发布并验证后才登记真实在线地址。

开源和自部署不自动意味着全部数据留在本地。数据流向取决于模型、解析、搜索和连接器配置。DeepTutor 为 Apache-2.0，Open Notebook 为 MIT；SurfSense 的主体许可与指定目录的附加许可应分别核对。[许可与验证记录](02-sources-and-verification.md)
