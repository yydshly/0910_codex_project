# System Prompts Leaks：我们的完整理解与研究结论

整理日期：2026-09-10

研究对象：[asgeirtj/system_prompts_leaks](https://github.com/asgeirtj/system_prompts_leaks)

固定研究版本：`f475e8b2b11ca7540a37234a451e9f085471bd94`，上游提交时间 2026-09-09 22:44:31 UTC。

本文整合前面的讨论、三篇研究笔记、来源索引和展示内容。它是当前研究的总入口；事实范围沿用固定快照，不代表对之后上游或产品状态的重新检查。

## 1. 我们现在怎样定义这个库

**它是持续维护的 AI 产品指令与配套材料档案。它的核心价值，是让部分原本难以观察的产品行为设计成为可阅读、可比较、可追溯的研究材料，为设计自己的 Agent 提供参考。**

这里的“提示词”范围比一句角色设定大得多。不同文件可能包括工作规则、工具定义、环境说明、技能文档、子代理职责、记忆约定、界面协议，以及经过整理或脱敏的会话结构。部分目录还包含脚本和组件源码。

仓库主要承担收集、分类和版本维护。对材料做中文解读、提炼设计模式，是我们这个研究子项目进一步完成的工作；将模式变成可运行、有效的助手，还需要自己的实现和实验。

可以分成三个连续环节：

| 环节 | 主要产出 | 当前由谁承担 |
| :--- | :--- | :--- |
| 获得并保存材料 | 提示词、接口说明、技能及配套文件、历史记录 | 上游维护者和贡献者 |
| 理解与解释材料 | 分类、中文解读、案例、来源判断、能力边界 | 我们的研究子项目 |
| 建立并验证产品 | 模型接入、工具执行、权限、状态管理、评测结果 | 后续开发与验证工作，当前未实现 |

## 2. 对最初理解的保留与修正

最初的判断是：“Codex、Claude Code 这类工具，是通过提示词控制大模型；这个库是在拆解这些 Agent 的底层。”这个判断抓住了重要的一层，但需要把范围说清楚。

**可以保留的理解：** 提示词确实参与组织 Agent 的行为。通过阅读它们，可以看到产品希望模型怎样理解任务、什么时候读取信息、如何选择工具、怎样分工、何时验证和结束。

**需要补全的理解：** Agent 的表现也取决于模型训练形成的能力、真实工具、上下文供给、权限与状态管理。提示词规定工作方式，程序提供实际执行条件。只有文本，无法自动产生文件编辑、联网、持久记忆或多代理调度能力。

**需要收窄的说法：** “拆解底层”更准确地指向可观察的指令设计层，以及文本所描述的工具和上下文协作方式。现有材料不能完整还原模型权重、训练流程、闭源后端或所有运行配置。

上游也不总是替读者完成了分析。很多地方提供的是原始材料或整理说明，需要研究者自己区分层次、核查来源并解释机制。

## 3. 一个 Agent 的能力由哪些部分共同形成

可对照阅读：[OpenAI 官方天气助手样例与组成图](05-official-agent-anatomy.md)。该补充使用官方 SDK 文档说明运行机制，与提示词档案的来源研究分开记录。

进一步理解过程：[Agent 如何推进任务](06-agent-task-loop.md)。这篇专题整合后续讨论，区分记忆与上下文、模型规划与程序调度，并说明状态、反馈、暂停和持续工作的关系。

以下是通用的概念拆分，用来理解档案，不是任一闭源产品的完整架构图，也不是所有产品都采用相同的指令顺序。

| 部分 | 负责什么 | 这类档案能提供什么线索 |
| :--- | :--- | :--- |
| 模型 | 理解输入、推断、生成回答或调用请求 | 名称和身份标签；不能提供权重或训练细节 |
| 指令与模式 | 定义角色、工作顺序、风格、完成标准 | 基础模板、开发者规则、规划等模式说明 |
| 上下文组织 | 提供任务、历史、项目、环境和相关资料 | 上下文栏目及使用约定；不一定包含实际内容 |
| 工具描述 | 告诉模型有哪些接口、参数如何填写 | 工具名称、参数定义、使用条件和限制 |
| 工具执行 | 读取、修改、查询、计算并返回结果 | 有时有配套代码；通常不足以重建全部服务 |
| 权限与隔离 | 决定哪些操作真正被允许 | 行为边界的文字描述；实际限制需由程序执行 |
| 调度与状态 | 管理任务、工具反馈、子代理和长期信息 | 分工、追踪、记忆与回传约定 |
| 界面与交付 | 渲染引用、交互组件和可下载产物 | 输出格式、展示协议与文件交付要求 |

典型工作循环是：

```text
用户任务 + 工作规则 + 相关上下文 + 可用工具定义
                         ↓
                   模型决定下一步
                         ↓
              直接回答，或生成工具调用
                         ↓
               运行程序执行并返回结果
                         ↓
             模型检查结果，继续处理或结束
```

例如“先读代码，再修改，最后运行检查”是工作规则。真正读写文件、启动检查、保存任务状态和限制写入范围，需要对应程序。提示词会影响模型的决策，但规则是否被遵循、是否改善结果，都要观察真实执行。

## 4. 它是一次性收集，还是自带收集与解析能力

**从已检查的提交历史看，它持续更新。** 新文件、纠错、版本变化、重命名与 PR 讨论都说明它不是仅在某一天采集完就停止的静态快照。我们固定一个提交，是为了让研究可以复核，不是说上游只更新了一次。

**从已检查的目录与贡献流程看，没有发现统一的通用自动提取、解析流水线。** 不能把它理解为“启动程序，输入产品名称，就能自动取得该 Agent 全部指令”的现成系统。

实际可确认的组织方式是：获得材料 → 按厂商和产品放置文件 → 提交或 PR → 校对和维护 → 用 Git 保存变化。[贡献指南](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/.github/CONTRIBUTING.md)主要规定 Markdown 原文与 PR 的提交方式。

需要保留两个区别：

- **持续收集不等于自动收集。** 贡献者可以各自使用不同方法取得材料，再进行人工提交。
- **目录里有脚本不等于有通用采集器。** 脚本可能是被收录技能的配套资源，其作用需要逐份检查。

我们还没有对所有文件逐份审计，所以“未发现统一流水线”是检查范围内的结论，不是证明每位贡献者都没有自己的辅助工具。

## 5. 材料的来源有哪些，怎样判断可信度

| 来源类型 | 已看到的依据 | 能说明什么 | 需要保留的边界 |
| :--- | :--- | :--- | :--- |
| 官方公开材料归档 | Anthropic 官方归档目录说明 | 有些条目来自公开发布，未必涉及非公开提取 | 仍需对应官方版本和归档日期 |
| 客户端本地资料 | Codex PR #166 的缓存模板说明 | 至少一个模板样本有明确的本地字段出处 | 不能推广到所有模型、产品和文件 |
| 运行时材料 | 贡献者对完整文本的说明 | 作者称材料来自运行时上下文 | 具体导出过程未必公开到可复现程度 |
| 环境或技能提取 | Claude Design Skills 的整理说明 | 可研究技能正文与配套结构 | 部分名称和描述元数据由整理者重建 |
| 特定捕获方式的作者声明 | Explore 样本中的捕获注记 | 该文件的作者陈述了获取方法和环境 | 本研究没有独立复现；不能移用到其他文件 |

仓库名中的“Leaks”不能证明所有文件来自同一种泄露方式，更不能证明存在统一的越狱算法。

为了避免把不同强度的依据混为一谈，我们按四类记录：

- **直接可见内容：** 固定提交里实际存在的文字、目录、行号、脱敏与禁用标记。
- **来源方陈述：** 贡献者或维护者对获取方法、校对方式和环境的描述。
- **机制解释或推断：** 根据公开源码解释可能的处理流程，或提出原因假设。
- **独立复现结果：** 在对应环境重新完成获取或执行并核对结果。本研究目前没有这类提取复现结果。

这不是对整个仓库统一打分。一份材料的正文可直接检查，其获取方法可能只有作者陈述，其完整性又可能仍未知。

## 6. Codex 提示词怎样取得：一个有具体出处的案例

选取的是 **Codex GPT-5.5 精简模板**，不是把所有 Codex 文件都视作同一个案例。

[PR #166](https://github.com/asgeirtj/system_prompts_leaks/pull/166)于 2026-07-08 合并。贡献者说明，精简文本取自本地 `models_cache.json` 的 `instructions_template` 字段，并与更大的运行时文本分开保存。

可以将这个缓存理解为客户端保存的模型目录资料。目录除了模型名称，还可能包含客户端组织请求时使用的指令模板。所谓提取，在这里就是定位对应模型记录，读取其中的字符串，保存为正常换行的文本。

```text
模型目录资料
    → 客户端获取并形成本地 models_cache.json
    → 定位目标模型与 instructions_template 字段
    → 导出精简提示词文本
    → 提交 PR
    → 对照新缓存、公开源码及运行时材料，校正后归档
```

[维护者跟进评论](https://github.com/asgeirtj/system_prompts_leaks/pull/166#issuecomment-4915783800)报告，使用当日客户端 0.142.5 的新缓存进行了交叉核对，并在[后续提交](https://github.com/asgeirtj/system_prompts_leaks/commit/8733d6c3ca22d7540e6e13132415de375ffb95d2)中修正精简文本。这里的历史操作仍属于参与者陈述。

我们另外读取了 2026-09-10 的 [OpenAI Codex 公开模型目录](https://github.com/openai/codex/blob/5a9eb145c4c05fcfc7158d7c25b80e1322eccae1/codex-rs/models-manager/models.json)、[缓存结构](https://github.com/openai/codex/blob/5a9eb145c4c05fcfc7158d7c25b80e1322eccae1/codex-rs/models-manager/src/cache.rs)和[模型信息处理逻辑](https://github.com/openai/codex/blob/5a9eb145c4c05fcfc7158d7c25b80e1322eccae1/codex-rs/models-manager/src/model_info.rs)。公开源码确实存在模型模板及相关处理机制。这支持对机制的解释，但不是重建 7 月 8 日的旧环境。

因此，这个例子不必假定作者通过让模型复述秘密指令取得文本。它已有更直接的缓存来源证据。读取一段模板字符串，也不涉及提取模型权重。

## 7. 基础模板、完整运行时文本与后端全貌的区别

**基础模板**是可重复使用的指令正文。**运行时上下文**可能进一步加入模式、开发者规则、工具、项目和环境信息、用户任务等内容。**产品后端全貌**还涉及实际服务、状态、权限以及观察点之外的处理。

因此，文件很长或名字带有 `full`，不意味着获得了服务端所有指令或全部配置。

| 文件 | 固定版本行数 | 当前理解 |
| :--- | ---: | :--- |
| OpenAI/Codex/gpt-5.6.md | 168 | 以工作和交流规则为主的 Codex 样本 |
| OpenAI/Codex/codex-full.md | 11,104 | 混合系统、开发者、用户、环境及大量工具说明的运行时档案 |
| OpenAI/gpt-5.6-sol.md | 1,845 | ChatGPT 产品侧的混合指令与会话上下文样本 |

Codex 完整文件后来从 `gpt-5.5-full.md` 更名为 `codex-full.md`，相关提交将工具与环境材料归于运行框架，而非某个模型专有内容。三个样本的完整路径、校验值和历史见[案例详解](03-codex-acquisition-chatgpt56.md)与[来源索引](03-source-index.json)。

关于获取方式，仍有四个明确限制：

- PR 没有公开足以复现完整运行时导出的工具或步骤，我们不能补写成确定的命令、日志或拦截方法。
- Codex GPT-5.5 缓存案例不能证明 Codex GPT-5.6 文件也以同样方式取得。
- 在已查资料中，ChatGPT 5.6 样本的具体获取过程仍缺少可复现记录。
- 即使观察到客户端已经组装的输入，也不能据此保证包含服务端之后可能补充的信息；加密网络抓包也不等于直接读到请求正文。

让模型复述指令属于另一种可能的研究途径，但其输出可能遗漏、改写或编造，必须有对照才能评价准确性。我们没有把这种一般可能性当成上述样本的实际来源。

## 8. 为什么同名模型的文本可能不一样

同名模型不保证每次收到同一份输入。产品模式、工具开关、项目、时间、账户配置及会话状态都可能影响上下文组成。具体因素需要逐项验证。

PR #166 中有人报告同一客户端版本出现模板差异。维护者推测可能是按账户分组的服务端实验，但没有公开内部实验配置。**差异报告可追溯，“一定是 A/B 测试”仍是推断。**

因此研究时应同时记录产品、模型标签、客户端版本、捕获环境、文件时间、入库时间、提交哈希和整理方式。文件更新也可能源于纠错或重命名，不能直接等同于产品能力升级。

## 10. 以 ChatGPT 5.6 为例，文件里究竟有什么

本次对象是 [OpenAI/gpt-5.6-sol.md](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/OpenAI/gpt-5.6-sol.md)。它位于 OpenAI 根目录，不在 Codex 子目录。文件名和首行是档案对样本的标注，不是本研究对所有 ChatGPT 账户配置的认证。

## 11. ChatGPT 样本的 16 个工具栏目

以下是 **16 个 Namespace 标题**，包含禁用项；不是我们已经验证的 16 项可用功能，也不等于 16 个独立工具函数。

| 命名空间 | 文本描述的方向 |
| :--- | :--- |
| python | Python 执行 |
| genui | 交互组件检索与运行 |
| web | 网络与结构化信息查询 |
| automations | 定时任务创建、修改和查看 |
| local | 将任务转交给另一工作环境 |
| python_user_visible | 面向用户展示的 Python 执行 |
| user_info | 与位置、时间有关的上下文 |
| summary_reader | 读取可安全分享的既往过程摘要 |
| container | 命令、进程输入和文件辅助操作 |
| personal_context | 检索个人相关上下文 |
| bio | 更新记忆 |
| api_tool | 发现资源、插件和工具 |
| image_gen | 图像生成与编辑接口 |
| hotline | 本地援助热线信息 |
| user_settings | 查询或调整用户设置 |
| canmore | 在该样本中明确标为禁用 |

接口声明能告诉我们“模型被怎样告知某个功能”，不能提供对应服务的全部实现、认证和部署环境。一个命名空间还可能包含多个函数，不能用标题数量衡量能力强弱。

同样，`summary_reader` 不证明档案保存了完整私有推理内容；脱敏栏目不能用于还原用户隐私；内部 `Juice` 数值不能直接换算成思考步数、智力或实际预算。详细程度设置主要提供回答风格线索。

## 12. 我们已经做出的 24 项能力解读

这些是**本站从代表性材料中选择的中文解读**。它们帮助理解文件中的工作约定，不表示上游只收录了 24 项，也不表示我们实际运行了这些产品。Codex 展示主要使用 GPT-5.4 指令样本，与前文的 GPT-5.5 获取案例、GPT-5.6 文件分析是不同研究对象。

| 产品与样本 | 已整理的能力主题 | 落地时还需要什么 |
| :--- | :--- | :--- |
| Codex：GPT-5.4 与独立规划模式文件 | 持续执行与验证；按风险代码审查；并行读取上下文；先规划暂不修改；保留用户已有修改 | 文件与差异读取、编辑和检查工具；模式限制与执行调度 |
| Claude Code：Opus 4.6 与 Explore、Plan | 任务拆解追踪；只读搜索子代理；分类长期记忆；区分操作影响；独立方案设计角色 | 任务状态、真实只读权限、记忆存储、子代理启动和回传 |
| Cursor：IDE 指令样本 | 编辑器上下文注入；工具接口发现；可定位代码引用；按任务加载技能；修改前先读文件 | 编辑器采集、工具认证、引用渲染、技能加载及文件操作 |
| Gemini CLI：CLI 指令样本 | 控制上下文成本；遵循工程规范；专用角色协作；把验证纳入任务；区分咨询与执行 | 范围搜索、项目上下文、角色调度、测试环境及权限管理 |
| Claude Design：技能与配套资料 | 设计方向指令；按产物拆分技能；工具定义与任务说明；起始组件资料 | 技能发现、实际工具、前端依赖、构建与产物呈现环境 |

完整来源关联保存在[展示目录数据](../web/public/catalog.js)。每项均拆成“指令要求 → 对任务的可能影响 → 程序依赖 → 研究边界”，避免把提示词写出的目标直接标成实测能力。

还完成了三个教学过程：修复登录问题、只做规划、子代理定位代码。它们通过逐步切换说明模型与程序的分工，使用的是本站编写的示例，不是原产品的真实执行日志。

## 13. 用两个例子把所有层次连起来

### 13.1 编码任务：修复登录后跳回登录页

用户提出修复目标；产品提供项目上下文与工具定义；工作规则要求先调查并持续完成任务。模型据此选择读取相关代码，程序实际读取并回传内容。模型提出修改，编辑工具应用变更，检查工具返回结果。模型再根据证据判断是否需要继续，最后报告改变、验证和未解决问题。

这个例子中，可以从档案借鉴的是调查、修改、验证和交付规则。真正的代码访问、修改、检查和权限控制，需要自己的工具环境。更积极地继续任务也不等于一定提高正确率，必须验证误修改、成本和完成率。

### 13.2 文件任务：根据销售表制作中文报告

用户输入和附件说明提供目标与资料入口；环境约定帮助确定文件在哪里处理；读取和检索接口取得实际数据；计算工具完成处理；文档或界面约定帮助生成可使用的结果；引用规则把结论与来源关联起来。

在这个过程中，模型不应仅凭文件名猜测数据。归档文本能够说明产品希望怎样选工具和交付结果，却没有附带这个例子的实际输入、工具结果与最终报告。因此它只能作为设计示例，不能作为端到端复现证明。

## 14. 它的核心价值究竟在哪里

你提出的“收集不同 Agent 的底层交互原理，再给我们做参考”，在限定为**可观察的指令、接口和流程设计**后，是对核心价值的准确概括。

| 价值 | 我们可以获得什么 | 怎样避免过度解读 |
| :--- | :--- | :--- |
| 提高可观察性 | 看到角色、工具、上下文、输出规范如何被描述 | 不把文字意图直接当成真实执行轨迹 |
| 学习产品设计 | 理解怎样组织规划、搜索、验证、记忆和交付 | 不认为所有规则都适合自己的业务 |
| 对比不同产品 | 比较职责、工具选择、引用和沟通策略 | 控制样本版本、产品模式和捕获差异 |
| 追踪演化 | 查看规则增删、纠错和版本变化 | 不把入库日期等同于上线日期 |
| 提出实验假设 | 将“先读再改”等规则变成可测试的候选设计 | 没有实验就不宣称收益 |
| 积累教学资料 | 用具体材料解释提示词与真实执行的关系 | 清楚标注原创示例与上游文本 |

有长期价值的结果，不只是收藏更多文本，而是积累“某条规则在什么模型、工具、任务和成本条件下有效”的证据。

## 15. 我们可以怎样迁移到自己的 Agent

已有三个迁移方向，均为本研究提出的设计建议，未做真实模型对照实验。

| 方向 | 可借鉴的规则 | 必须补齐的实现 | 评测重点 |
| :--- | :--- | :--- | :--- |
| 能交付任务的编码助手 | 明确任务后调查、实施、验证和报告 | 搜索读取、范围受限的编辑、检查执行和反馈 | 完成率、正确率、误修改、耗时、调用成本 |
| 只读代码调查助手 | 专注定位文件和符号，带依据说明范围 | 只读工具集合、程序级禁止写入、结果回传 | 定位准确率、遗漏率、是否确实无法写入 |
| 记住团队约定的助手 | 区分长期信息与临时细节，按任务读取约定 | 持久存储、访问控制、检索、查看更新删除 | 适用性、过期处理、冲突、跨项目误用 |

实践时按下列顺序推进：

1. 选一个具体任务，而不是先复制整个产品的全部提示词。
2. 找一份相关材料，保存版本、来源和环境信息。
3. 提炼少数规则，保留每条规则与来源的对应关系。
4. 改写工具名、业务条件和完成标准，移除不适用或互相冲突的指令。
5. 实现工具、权限与状态管理，先保证流程真实可运行。
6. 固定模型、任务、工具、采样设置和预算，比较基础方案与候选规则；必要时重复试验。
7. 保存成功与失败案例，再决定保留、修改或移除规则。

例如只读权限必须由程序保证。“不要修改文件”的提示词可以说明角色边界，但不能独自承担访问控制。多个产品规则直接堆叠，也可能产生模式冲突、无效工具引用和额外上下文成本。

## 16. 后续可以扩展成什么

以下为研究建议，不是当前上游或本站已经完成的全部功能。

| 优先级 | 方向 | 具体产出 | 当前基础与缺口 |
| :--- | :--- | :--- | :--- |
| P0 | 来源与可信度记录 | 每条材料的来源类型、时间、环境、哈希、整理方式和验证状态 | 已有固定快照与三个样本索引；尚无全库逐条来源档案 |
| P1 | 中文分类与检索 | 原文与中文解释分开，按任务、产品、工具和规则搜索 | 已有目录浏览及 24 项精选解读；尚无全库中文语义检索 |
| P1 | 版本与语义比较 | 区分格式改动、规则变化、工具增删和重建元数据 | 已分析部分路径历史；尚无自动比较工具 |
| P2 | 模块化规则库 | 每个模块附目的、依赖、冲突、适用条件和来源 | 已有三个迁移示例；尚无经验证的通用模块库 |
| P2 | 受控评测工作台 | 对比加规则前后的效果、成本和失败类型 | 已提出评测方法；未接入模型开展实验 |
| P3 | 研究知识库或 MCP 服务 | 只读搜索、原文定位与版本查询，结果携带出处 | 尚未实现服务 |
| 后续 | 辅助更新流程 | 检查上游变化、解析已取得材料、提示研究者复核 | 可以辅助维护；不能因此假设能自动取得闭源产品全部指令 |

可行的先后顺序是完善来源记录，再做中文索引和版本比较，之后选择小任务建立评测。知识库返回的上游指令应当作为被研究的数据；不应自动提升成研究助手自身的系统指令。

## 18. 仍需回答的问题与常见误读

| 问题或说法 | 当前准确回答 |
| :--- | :--- |
| 它会自动拆解任何 Agent 吗？ | 目前证据支持资料收集与维护；未发现统一通用拆解服务。 |
| 它已经公开了 Agent 的完整底层吗？ | 公开材料能揭示部分指令、接口和流程；完整运行系统仍有大量未知。 |
| 这些文件都可靠吗？ | 需要逐条评价；文件存在、作者声明和独立复现是不同证据。 |
| Codex 5.5 的获取方法适用于 ChatGPT 5.6 吗？ | 不能据现有证据这样推断。 |
| 复制提示词就能复制产品能力吗？ | 还需要模型、工具、上下文、权限、状态与实际评测。 |
| 更长的提示词或更多工具就更强吗？ | 数量不能替代任务效果与成本的证据。 |
| 文件里有记忆栏目，就公开了真实用户记忆吗？ | 所研究 ChatGPT 样本的具体私有栏目已脱敏。 |
| 看到工具接口，就表示现在能用吗？ | 需要对应服务、权限和环境；样本中还包含明确禁用项。 |
| 文本更新代表模型升级吗？ | 可能是规则变化，也可能是捕获、纠错或整理变化。 |
| 我们的 24 项解读就是上游全部成果吗？ | 是代表性精选，不是全量内容或实测能力清单。 |

后续最值得补证的是：重点文件的可复现来源、不同版本和账户的差异原因、捕获与重建部分的边界，以及规则迁移后的实际收益。尚未得到的答案应继续保留为问题，不用看起来合理的解释填补证据空白。
