# System Prompts Leaks：能力、原理、场景与扩展

研究日期：2026-09-10

研究版本：`f475e8b2b11ca7540a37234a451e9f085471bd94`

研究方法：GitHub 目录检查、代表性文件阅读、工具执行机制的官方文档交叉核对。

## 1. 核心定位与能力

这是一个持续维护的 AI 产品提示词档案。主要价值是让读者观察各类助手的角色设定、输出格式、工具调用约定和任务流程。

[上游 README](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/README.md) 按厂商与产品提供索引。研究版本包含 430 个 Markdown 文件，但这不是 430 个独立产品或系统提示词：其中包括说明、技能文档、历史版本与重复汇总。目录还包含配套 JS、TS、Python 和组件材料，因此也不能把整个仓库概括为只有纯文本。

| 可直接利用的内容 | 实际用途 | 能力边界 |
| :--- | :--- | :--- |
| 多产品提示词文件 | 对照角色、风格、工具使用与任务完成标准 | 文件存在不代表其真实性、完整性或当前有效性已被认证 |
| 历史文件与 Git 提交 | 比较某个文件在不同提交中的变化 | 入库时间不等于产品上线时间；差异也可能来自捕获或整理方式变化 |
| 工具说明及参数定义 | 学习工具接口如何向模型描述 | 工具接口文本不能替代执行实现、权限与服务 |
| Skills 与配套资料 | 研究任务流程如何分模块组织 | 可能依赖原产品环境，未验证可以直接迁移 |
| PR 贡献流程 | 持续增加与更新资料 | 本次检查未发现统一的逐条来源认证或效果评测机制 |

[贡献指南](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/.github/CONTRIBUTING.md) 要求在相应目录创建 Markdown 文件，保留提示词原始文本，并通过 PR 提交。它没有描述一套适用于所有产品的自动提取算法。

## 2. 技术原理

### 2.1 仓库如何工作

主要流程是：获得或收集材料 → 按厂商和产品归档 → 提交或 PR → 用 Git 追踪版本 → 读者阅读、比较与再研究。

在本次检查的根目录和贡献文档中，没有发现统一推理服务、统一应用启动入口或通用提示词提取工具。部分子目录包含可执行代码，不应据此推断整个仓库是可直接运行的 Agent 框架。

### 2.2 文件中的提示词如何影响 AI

以下是用于理解材料的通用机制，不是对任一闭源产品后台的完整复原：

1. 产品把角色、工作规则、用户任务、会话上下文和工具定义交给模型。
2. 模型结合训练形成的能力与这些上下文，生成回答或结构化工具调用。
3. 宿主程序或服务端实际执行工具，并把结果交回模型。
4. 模型继续判断、调用工具或完成回答。

[Anthropic 官方工具文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) 明确区分模型生成调用与客户端或服务端执行工具。这也解释了为什么复制“可以搜索、编辑文件”的描述，不会自动给一个聊天模型增加搜索或文件访问能力。

提示词可以约束角色、流程、风格和工具选择，但无法单独提供模型权重、外部知识库、执行权限、持久记忆或完整的运行时系统。规则是否有效也需要通过实际行为测试判断。

### 2.3 代表性材料揭示了什么

- [Cursor 文件](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/Cursor/cursor.md)：包含工具使用、修改代码、代码引用、任务管理与 MCP 工具发现等约定。可借鉴“把什么情况下调用工具、如何展示结果写清楚”的设计。
- [Gemini CLI 文件](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/Google/gemini-cli.md)：包含上下文效率、工程规范、任务流程与子代理描述。可研究复杂任务如何分解、如何控制读文件和调用工具的成本。以上是文件内容观察，未验证真实产品是否逐项遵循。
- [Claude Design Skills 说明](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/Anthropic/claude-design/skills/README.md)：按技能拆分文档，并关联工具定义与起始组件。说明还指出部分 YAML 元数据由整理者根据技能列表重建，分析时必须区分捕获文本与重建元数据。

### 2.4 “Leaks”是否意味着全部来自同一种泄露方式

不能这样推断。[官方归档说明](https://github.com/asgeirtj/system_prompts_leaks/blob/f475e8b2b11ca7540a37234a451e9f085471bd94/Anthropic/official/README.md) 表示该目录归档 Anthropic 公开的提示词；其他材料可能标注为从运行环境捕获。贡献指南主要规定提交形式，没有为每份文件提供统一且可独立复现的取证过程。

本次确认的是“仓库收录了这些内容及来源声明”。没有验证所有条目确实来自其声称的产品，也没有复现提取手法。不能仅依据项目名称推断使用了某种通用越狱方法。

## 3. 使用场景

以下是基于材料结构提出的用途，不代表仓库自带对应应用。

| 场景 | 如何使用 | 应如何验证 |
| :--- | :--- | :--- |
| 开发企业内部助手 | 提炼角色、澄清问题、引用依据和完成条件，改写为业务规则 | 用真实但脱敏的典型任务评估正确率与可用性 |
| 设计编码 Agent | 研究先理解项目、再修改、再验证的流程以及工具描述 | 在固定任务集比较完成率、误修改和耗时 |
| 产品行为研究 | 比较不同产品的输出风格、引用与用户沟通规则 | 区分文本意图和真实运行行为 |
| 提示词版本研究 | 比较同一文件的固定提交，记录规则变化 | 控制捕获环境、工具开关与版本因素 |
| 教学与团队培训 | 用短片段解释提示词、工具定义与实际执行的关系 | 用自有助手演示，避免把描述当成已有能力 |
| 自有系统的安全测试 | 从权限边界和外部数据处理规则中设计测试案例 | 在授权环境验证控制是否由程序真正执行 |

更实用的学习方式是选择一个业务任务、提取少数相关规则，然后做对照测试。整段堆叠不同产品的提示词可能引入冲突、无效工具引用和额外上下文成本。

## 4. 可扩展方向

以下为本研究提出的完整扩展方向。当前已完成固定版本索引、少量样本来源记录和精选中文解读；各方向的完整工具链尚未实现，具体进度见[完整理解与研究结论](04-complete-understanding.md)。

| 优先级 | 方向 | 最小实现 | 预期价值 |
| :--- | :--- | :--- | :--- |
| P0 | 来源与可信度记录 | 记录产品、模型、捕获时间、入库时间、来源类型、原始链接、提交哈希、是否完整与验证状态 | 让比较与结论有可追溯依据 |
| P1 | 中文索引与检索 | 保留原文，单独保存中文摘要、标签与译文；按产品、任务和规则类别筛选 | 降低阅读成本，避免覆盖原始证据 |
| P1 | 语义版本比较 | 按角色、工具、工作流和输出规范切分，再显示增删与规则变化 | 区分格式整理和真正的指令变更 |
| P2 | 模块化提示词库 | 将通用模式改写为有适用条件、依赖和冲突说明的模块 | 帮助团队组合自己的助手规则 |
| P2 | 受控评测工作台 | 固定模型、工具、任务、采样参数与预算，比较基础提示词和候选规则 | 验证规则是否提升完成率，以及成本变化 |
| P3 | 研究知识库或 MCP 查询服务 | 暴露只读搜索、查看原文和版本对比接口；每条结果携带出处 | 让研究助手按需引用资料 |

实现检索或知识库时，档案中的指令应作为被分析的数据保存与呈现；不要自动把检索结果提升为运行助手的系统指令。

建议先完成“来源记录 + 中文索引 + 版本比较”的小型原型。等条目结构稳定后再增加评测；一开始直接做提示词生成器，会难以判断生成结果来自何处、是否有用。

本项目当前结论：它适合作为 AI 产品行为设计的研究资料。能否转化为稳定的产品能力，需要在自己的运行环境中补齐工具实现、上下文组织与评测。
