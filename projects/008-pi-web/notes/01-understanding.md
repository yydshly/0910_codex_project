# Pi Web：把 Pi 引擎组织成浏览器工作台

研究日期：2026-09-10。固定提交：`b1a72962d385db4a82b93ad5802e9024d5b44874`；package.json 版本：0.9.0；许可证：MIT。以下“已实现”表示源码中存在实现，不表示本次做过实际模型调用或跨平台验证。

## 先把定位讲清楚

Pi Web 是基于 Pi SDK 的应用层二次开发。它同时提供网页前端与 Node.js 服务端，后者在同一进程内创建 Pi 智能体会话。因此安装并运行 Pi Web 后，就已经包含了网页和背后的智能体执行服务，无需先单独启动 Pi 服务端。

它可呈现类似 AI 编程工作台的工作方式，但使用的是 Pi 引擎，不是 Codex 后端；不能把“工作方式相似”理解为质量、权限和产品能力完全一致。

| 层次 | 职责 | 运行位置 |
| :--- | :--- | :--- |
| Pi Web 浏览器前端 | 接收任务、显示消息与工具结果、文件预览、配置与会话管理 | 浏览器 |
| Pi Web 服务端 | 路由、会话生命周期、文件与配置接口、事件转发 | 启动 Pi Web 的电脑 |
| 内嵌 Pi 引擎 | 组织智能体运行、调用模型、执行可用工具 | Pi Web 服务端进程 |
| 模型服务 | 理解需求、推理、生成内容及工具调用 | 取决于模型服务配置 |

“本地工作台”不等于“模型必定离线运行”。“浏览器客户端”也不意味着可以只部署静态网页就获得文件修改和命令执行能力。

## 我们最终确认的理解与 Codex 对比

**直观理解：Pi Web 让人通过浏览器，使用一套与 Codex 桌面工作台相似的 AI 编程工作方式。准确理解：它基于 Pi SDK 开发，包含网页与服务端；浏览器是操作入口，Pi 是执行引擎，所配置的模型负责推理。**

这回答了讨论中的四个问题：

1. **是一个 Codex 客户端吗？** 不是。它不会因为界面类似就连接 Codex 后端，运行核心明确集成 Pi SDK。
2. **只是浏览器前端吗？** 不是。仓库同时提供 Next.js 前端与本地服务端，服务端在同一进程内创建 Pi 会话。
3. **必须先安装、启动独立 Pi 服务吗？** 不需要单独启动。启动 Pi Web 已包含服务端与 Pi 引擎；已有 Pi 配置和会话可在相同文件环境下复用。
4. **与 Codex 的差别只是 App 和浏览器吗？** 这是理解使用体验的有效类比，但只覆盖界面形态。两者的运行体系、模型组合、工具集、权限和集成仍不同。

| 对比维度 | Pi Web | Codex 参照及比较意义 |
| :--- | :--- | :--- |
| 用户做什么 | 输入需求、让智能体操作项目、检查过程和结果 | 桌面编程体验有相似闭环，可用来理解它属于哪类工具 |
| 交互入口 | 以浏览器为工作界面 | 本文以桌面体验作参照；Codex 也有 CLI、IDE 等入口，不能概括为“Codex 只有 App” |
| 执行系统 | Pi Web 服务端内嵌 Pi SDK，调用配置模型及工具 | Codex 使用自身的智能体运行体系，不是同一个后端换界面 |
| 可研究、复用的部分 | 会话管理、事件流、工具结果展示、文件与终端、模型和扩展配置 | 比较帮助我们分清通用工作台设计与具体执行实现，寻找二次开发的复用点 |
| 能否判断效果相等 | 不能，只确认源码中具备这些能力 | 尚未在相同任务、模型条件、预算与权限下对测，不作优劣或等效结论 |

Codex 参照依据：官方[桌面应用说明](https://learn.chatgpt.com/docs/app)说明从桌面选择 Codex 开展软件开发；[Codex CLI](https://learn.chatgpt.com/docs/codex/cli)说明查看文件、修改代码、运行命令及其他入口。资料核对日期为 2026-09-10。此处不把桌面产品整体当作仅有一个聊天界面的程序，也不把不同入口的功能无条件互相套用。

**比较的意义是定位与复用，而非做未经验证的能力排名。** Pi Web 值得研究之处，是用可读的开源应用代码，把已有智能体引擎组织成一个可以操作、追踪、配置和扩展的工作台。模型决定推理与生成，智能体系统决定如何推进和执行任务，界面决定用户如何发起、观察和管理这些任务。

## 同类产品与对我的意义

这次研究关心三个问题：库能做什么、在同类工具中如何定位、怎样服务于当前的研究与开发。对外摘要因此以能力、同类与用途为主；前后端、模型和 SDK 的具体分工放在完整分析中。

| 同类参照 | 官方资料确认的能力 | 用来理解 Pi Web 的角度 |
| :--- | :--- | :--- |
| Codex | 在项目中读取与编辑文件、运行命令，提供桌面、CLI、IDE 等入口 | 相似的任务执行闭环，入口形态与执行系统需分开理解 |
| Claude Code | 阅读代码库、编辑文件、运行命令，并提供终端、IDE、桌面与浏览器入口 | 浏览器和桌面可承载同一类编程工作方式，不能只按入口判断底层引擎 |
| Cursor Agent | 搜索代码、编辑文件和运行终端命令，由指令、工具和模型构成智能体工作方式 | 比较工作台怎样组织项目上下文、工具与结果检查 |

**对当前工作的用途判断：**

1. **开源项目研究。** 将克隆后的源码目录作为上下文，读取关键模块、形成带来源的中文笔记，查看产物和版本差异。项目编号、许可证、来源和验证规范仍需研究 Skill 或仓库约定落实。
2. **个人开发管理。** 通过浏览器集中看任务对话、文件与命令结果，使用会话分支讨论不同方案，必要时用 worktree 管理独立代码目录。
3. **自建领域助手。** 参考或复用会话生命周期、工具事件展示、文件预览、模型与 Skills 配置；接入自己的检索、报告或审查工具。Pi Web 的价值在于提供应用层基础，领域能力仍需实现。
4. **帮助选型。** 有自托管、浏览器入口或二次开发需求时再进一步试用；如果现有 Codex 等工具已经满足需求，研究这个库也可以只服务于学习和复用，而不必迁移日常工作。

上述为根据当前任务和源码能力作出的用途分析，尚未证明节省时间、降低成本或提高输出质量。

## 已实现的六类能力

### 1. 智能体编程与工具选择

`lib/tool-presets.ts` 定义纯聊天、只读、默认和完整四种工具预设。只读内置工具为 read、grep、find、ls；默认包含 read、bash、edit、write；完整模式合并这些工具。Pi 引擎负责调用和执行，Pi Web 负责选项、会话和结果展示。

需要区分工具选择与强隔离：普通非空工具预设会结合扩展工具运行。只读内置工具集合不自动证明所有加载扩展都只读，也不等于操作系统沙箱。纯聊天模式则有专门的资源加载策略，不加载普通扩展、技能、模板和主题。

### 2. 会话浏览、恢复与分支

按项目组织对话，恢复、重命名、导出和删除会话。历史浏览读取 JSONL 数据，不必为每次查看都创建活跃智能体。运行时可查看上下文使用、费用和压缩情况。

- 独立分叉：从历史节点创建新的会话文件，通过 parentSession 关联显示。
- 会话内分支：使用 parentId 构建消息树，在同一个会话文件中选择不同路径。

两者都是会话上下文的分支，不代表代码文件被还原到历史状态。代码版本需通过 Git 管理。

### 3. 文件工作区与 Git worktree

支持项目文件浏览、上传、Git 差异和多种文件预览。预览格式包括源代码、Markdown、图片、音频、PDF、DOCX；这是界面的呈现能力，不意味着模型可以直接原生处理所有格式。

worktree 用不同工作目录承载同一仓库的不同任务；会话可归组到同一个主项目。删除存在未提交修改的 worktree 会返回冲突状态，要求界面处理。它是代码工作目录隔离，不是安全沙箱。

### 4. 模型、插件包与 Skills

通过网页配置模型、提供方登录与 API Key，进行模型连通性测试。插件管理复用 Pi 的 SettingsManager 与 DefaultPackageManager，资源加载复用 DefaultResourceLoader。包可包含扩展、Skills、提示词模板和主题。

与 Pi 共用默认位于 `~/.pi/agent` 下的数据；会话路径为 `sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`。命令行与网页共享已有记录的前提是能访问同一套文件环境，不应推断为两个活跃客户端可以无条件同时修改同一会话。

### 5. 网页终端

xterm.js 呈现终端，node-pty 提供服务端真实 Shell。输入经请求发送，输出经 SSE 推送。输出带递增位置，重连时获取缺失部分；服务端保留有限的输出历史，并不是完整终端屏幕快照。

终端标签可保留身份和布局；服务重启或终端过期后，不会静默创建替代进程。原生模块是否能加载需在实际安装环境验证。

### 6. 内置子智能体

当前源码包含内置子智能体扩展，默认关闭。启用并重载会话后，父智能体可使用 Agent、get_subagent_result、steer_subagent 来委派任务、读取结果和发送指导。

子智能体使用可检查的 Pi 会话，可配置模型、提示词、工具、上下文继承与资源加载；支持前台等待及后台完成通知。子会话不自动获得独立文件系统；源码还排除了子智能体继续暴露保留的子智能体控制工具，不应把它宣传为任意层级递归 Agent 平台。

## 技术原理：一次任务如何推进

1. 用户在浏览器选择项目、模型与工具，然后提交任务。
2. Next.js 路由接受请求，`startRpcSession()` 创建或复用会话包装器。
3. `createAgentSessionServices()` 准备配置与资源，`createAgentSessionFromServices()` 创建进程内 Pi 会话。
4. 包装器调用 `inner.prompt()`；Pi 将上下文提交给配置的模型，并执行模型请求的工具。
5. `inner.subscribe()` 收集事件；服务端通过 SSE 推送到浏览器。
6. 前端渲染内容和状态，必要时通过状态查询补偿断线、后台标签和漏收事件。
7. 会话记录保存在本地 JSONL 文件，供后续恢复、浏览和分支。

尽管核心模块命名为 rpc-manager，当前实现没有要求用户另起 RPC 智能体服务。全局注册表按会话保存包装器，并避免重复初始化；空闲会话有回收机制。可常驻进程、本地文件系统、原生终端模块与持续事件连接是部署时的重要条件，因此 GitHub Pages 只能承载本研究说明页，不能运行上游本体。

## 使用场景

| 场景 | 可复用的能力 | 实际边界 |
| :--- | :--- | :--- |
| 个人编程 | 任务对话、工具执行、文件与差异、终端 | 模型输出和修改仍需验证 |
| 开源代码研究 | 检索源码、阅读文件、分叉研究思路、保存笔记 | 结论要标明源码证据与运行验证区别 |
| 多方案开发 | 会话分支与独立 worktree | 两种分支需要分别管理 |
| 可信环境远程使用 | 浏览器访问自己的开发机 | 执行发生在服务端机器；远程连接需正确认证和加密 |
| 垂直领域助手 | Skills、插件、提示词模板和模型配置 | 专业工具与业务流程仍需开发 |

对于本研究仓库，可以增加统一的研究 Skill，让智能体按编号目录输出能力、原理、许可和证据，然后用网页文件预览与 Git 差异审阅。这里的流程属于扩展方案，并非 Pi Web 自动内置本仓库的规则。

## 可扩展方向（建议，非已实现）

1. **领域研究流程**：源码检索、版本固定、引用校验、统一报告与实验记录。
2. **研发任务闭环**：接入 Issue、测试和 CI、准备待审查 PR，并设置人工确认点。
3. **子智能体协作**：在现有委派上增加依赖调度、预算、独立工作目录和结果验收。
4. **知识库**：增加索引、增量更新、检索与出处绑定。
5. **执行评估**：把现有事件和会话记录组织成可查询的执行数据，定位失败与比较模型效果。
6. **团队服务**：补充账号、项目授权、凭据隔离、执行沙箱、配额和审计。

现有认证主要是可选共享密码，默认绑定回环地址。文件访问边界约束浏览接口，不能推导出命令工具被限制在同样目录。自托管部署的权限应依据实际配置评估。
