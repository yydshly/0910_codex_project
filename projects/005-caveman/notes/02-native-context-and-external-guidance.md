# Codex 已有上下文管理，Caveman 的增量价值在哪里？

研究日期：2026-09-10。Caveman 研究版本：`15581d14007fd01fb3f132016741962f34936ca2`。Codex 对照依据：当日查阅的 OpenAI 官方配置与命令文档。本文整理当前讨论形成的理解；没有安装 Caveman、修改 Codex 配置或实测二者叠加效果。

## 1. 当前理解

**Codex 等 Agent 工具已经自带上下文管理。Caveman 更值得研究的部分，是具体压缩策略、恢复机制及其相对于原生能力的增量收益。**

**摘要：Caveman 的输入优化运行时在模型调用前按类型精简选定内容，保存原文以便恢复，并在不适合压缩时回退。其价值主要在于可研究、可复用的专用规则与恢复设计；是否能在原生 Codex 基础上进一步改善效果，仍待验证。两者能力部分重合，但不代表具体实现和效果完全相同。本研究及其架构图不表示我们建议叠加使用，也不表示已经确认叠加有收益。**

仅证明“它能减少输入”不足以说明有必要在 Codex 前再增加一层工具。需要进一步判断：它删掉的是什么、会不会删掉任务所需信息，以及原生机制是否已经处理了同一类问题。

我们保留以下判断：

1. **本研究重点是输入优化运行时。** Caveman Engine / Proxy 精简模型即将读取的内容；独立的回答 Skill 仍然关注输出风格，不能说整个仓库不处理输出。[C1]
2. **工具输出也是模型输入。** 日志、测试结果、文件读取结果等会在后续请求中进入模型上下文。
3. **压缩规则值得研究，但不只是提示词。** 其中包含内容解析器、结构转换、片段选择、token 检查和恢复约束。[C2][C3]
4. **上下文管理不是 Caveman 独有能力。** Codex 已提供自动整理、手动 compact、工具输出预算等机制；实验性管理还引入笔记与可搜索历史。[O1][O2]
5. **是否值得使用，需要对照验证。** “原生 Codex”是基线，而不是一个完全没有上下文管理的 Agent。
6. **能力重合不等于完全相同。** 目标重合、整理手段部分重合，具体规则可能不同；实际效果需要端到端对照，不能仅凭架构图下结论。

## 2. 外部引导与上下文整理架构

![外部文字引导和可执行规则分别影响 Codex 与 Caveman；原生 Codex 可直接调用模型，也可经过可选 Caveman 层；工具结果回填、原文恢复和对照评估形成整体关系](../assets/external-guidance-architecture.png)

图 3：外部引导与原生上下文管理的关系。来源：依据 OpenAI 官方文档与 Caveman 固定版本源码原创整理，非运行截图，也不表示当前会话已经部署 Caveman。[查看 SVG 矢量图](../assets/external-guidance-architecture.svg)

本图将“外部引导”解释为两种不同机制：

- **文字引导：** 用户要求、AGENTS.md、Skill 和配置中的提示词影响 Agent 怎样搜索、读取、记录与汇报。它们需要由 Agent 或相应运行时执行；文字本身也占上下文。普通 Skill 不会因此自动获得修改全部模型请求的能力。
- **可执行规则：** 压缩程序直接处理候选输入，比如解析代码结构、筛选日志、精简重复数据。实际变换发生在程序中，不依赖模型把“请精简”理解成某个确定算法。

图中的代理路径表示一种集成位置，不代表所有接入都严格按同一顺序处理，也不代表 Caveman 可以读取、重建或再次压缩所有 Codex 内部状态。模型请求额外细节后，恢复由 Agent 调用工具完成；模型服务不会直接访问本地数据库。

**“Codex → Caveman → 模型”只表示可选路径，不表示我们建议叠加使用，也不表示已经确认叠加有收益。** 原生 Codex 无需 Caveman 即可进行上下文管理和模型调用。

## 3. Codex 已经具备什么？

以下为官方文档能够确认的能力，不等同于当前桌面会话的启用状态：

| 机制 | 官方入口 | 作用与边界 |
| :--- | :--- | :--- |
| 自动历史整理 | `model_auto_compact_token_limit` | token 达到阈值触发；未设置时使用模型默认值 |
| 手动整理 | `/compact` | CLI 命令，可总结当前对话、释放上下文空间；不推定各端具有相同 UI |
| 单次工具结果预算 | `tool_output_token_limit` | 控制单个工具结果存入历史的 token 预算；不等于按领域理解并保留所有重要内容 |
| 历史压缩提示词配置 | `compact_prompt`、`experimental_compact_prompt_file` | 文档提供覆盖入口；具体生效路径与运行时实现有关 |
| 实验性上下文管理 | `features.context_management.experimental_mode` | 使用笔记和可搜索历史保留细节；文档标记默认关闭且有登录、套餐条件，不推定当前会话启用 |

依据：[官方配置参考 O1](https://learn.chatgpt.com/docs/config-file/config-reference)、[官方命令说明 O2](https://learn.chatgpt.com/docs/developer-commands#built-in-slash-commands)。

还需区分官方配置中的 `features.enable_request_compression`：它指支持条件下用 zstd 压缩传输请求体。**网络传输字节减少，不等于模型读取的 token 减少。** 服务端解压后内容仍然相同，不能拿它与语义精简或上下文整理的收益直接比较。[O1]

## 4. 两者如何重叠，哪里可能不同？

| 比较维度 | Codex 原生管理 | Caveman 可研究部分 |
| :--- | :--- | :--- |
| 主要位置 | Agent 自身任务流程与上下文生命周期 | 外部适配、工具入口或请求代理 |
| 已确认的整理方式 | 历史整理、输出预算、可配置提示词；实验性笔记与搜索历史 | 针对日志、代码、JSON 等的结构压缩，另有预算模块 |
| 任务流程 | 自身组织工具执行与后续模型请求 | 压缩层与宿主任务流程配合，不能仅凭压缩器替代完整 Agent |
| 找回细节 | 能力随模式与工具而异；实验选项有可搜索历史 | 为有损变换保存原始字节，提供恢复引用 |
| 核心研究问题 | 当前原生策略怎样选择和保留信息 | 外部规则能否在同等质量下再减少成本 |

不能简单概括为“Codex 只压历史、Caveman 只压工具输出”。Caveman 也有历史和上下文预算能力，Codex 也管理工具输出；二者存在真实重叠。[O1][C1][C4]

这不是一份逐行对照 Codex 源码后的完整能力清单。官方文档没有说明某种领域压缩规则，并不构成 Codex 绝对没有该规则的证据。

## 5. 压缩规则的价值，取决于任务

以下是用于解释机制的假设场景，不是实测结果：

| 输入 | 当前任务 | 合适的取舍 | 容易出错的取舍 |
| :--- | :--- | :--- | :--- |
| 代码文件 | 列出模块接口 | 保留类型、函数签名与导入关系 | 过早读取所有实现，增加上下文 |
| 同一代码文件 | 查找函数内部边界错误 | 读取相关函数完整实现及调用条件 | 省略函数体，把问题证据一起删掉 |
| 大量日志 | 定位失败原因 | 保留错误、相邻上下文、时间和关联标识 | 仅按级别删除普通日志，丢失前因 |
| 重复 JSON 数据 | 查找异常记录 | 保留异常行和判断异常所需字段 | 固定取前几条，遗漏中间的异常 |

Caveman 的 cgo 代码压缩器使用 Tree-sitter 保留结构并省略函数体，再重新解析验证。这个实现能说明“如何缩短代码表示”，但不能证明“被省略的函数体与当前任务无关”。语法有效也不等于行为等价。[C5]

所以，我们真正需要审查的是五个问题：

1. **删什么？** 明确每类变换的保留与丢弃规则。
2. **为什么能删？** 依据内容形态、任务相关性还是经验阈值？
3. **何时不删？** 信息不足、解析失败、没有变短或无法恢复时如何处理？
4. **删错了怎么办？** 原文能否准确取回，Agent 是否知道缺少了什么？
5. **总体是否划算？** 计入恢复调用、提示词开销、缓存变化和额外延迟后是否仍然有收益？

## 6. 我们的使用判断

**如果主要使用 Codex，不应仅因为 Caveman 宣称“压缩上下文”就默认再加一层代理。** 先用原生能力完成任务；当某类工具结果持续造成明显冗余时，再评估针对该类材料的外部处理。

研究价值主要在于学习其内容专用规则、模块划分和恢复接口。工程价值则必须由任务对照证明。对自建 Agent 或需要统一处理多种客户端的场景，独立压缩层可能更方便；这是架构层面的推断，尚未在本研究中验证。

额外压缩可能与原生策略互补，也可能带来反复恢复、重复概括、缓存变化或更多调用。当前没有足够证据判定 Caveman 对本仓库工作流是净收益。

## 7. 下一步怎样验证增量价值？

建议分成两个阶段，以下仅为待执行方案：

**规则审查：** 逐个阅读日志、代码、JSON 压缩器，用正常样例与故意放在边缘位置的关键证据检查保留规则。记录丢失的信息、回退条件与恢复能力。

**端到端对照：** 在相同模型、任务、初始仓库状态和工具权限下，比较以下实验组：

| 实验组 | 用途 |
| :--- | :--- |
| A：原生 Codex | 衡量现有上下文管理的基线 |
| B：原生 Codex + 简短的读取指导 | 判断更精准的检索、分段读取能解决多少问题 |
| C：原生 Codex + 指定 Caveman 输入压缩规则 | 衡量可执行规则的额外收益；其他设置尽量保持一致 |

只在可配置、兼容的环境中隔离比较输入压缩；不要同时启用输出 Skill 或其他优化后，把全部变化归因于输入压缩。每组重复运行，并保留失败和负收益样例。

记录任务正确率、是否需要人工补救、服务商报告的总输入与缓存分类、输出用量、恢复次数、总耗时及实际费用。若按订阅或请求计费，不把 token 降幅直接换算成账单降幅。优先判断是否正确完成任务，再评估成本。

此前上游百分比不能替代这个对照：输出 Skill 的公开原始结果存在证据缺口，代理报告也未提供完整可独立复现的运行产物。[C6][C7]
