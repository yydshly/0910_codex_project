# AnySearch Skill：能力、原理、场景与扩展

研究日期：2026-09-10。代码基线：`15b7ea5039983c9dee328be8c7c609f3eb86058e`，技能版本 3.1.1。

## 1. 定位

这个仓库提供的是 **AI Agent 访问 AnySearch 服务的技能规范和客户端**。它把何时搜索、如何选择领域、如何填参数、如何并行和读取正文组织成 Agent 可以遵循的流程。

实际搜索、数据源访问和正文抽取在 `api.anysearch.com` 完成。仓库没有提供搜索后端、网页索引、爬虫集群或排序模型。因此可以研究它的 Agent 集成方式，无法凭此仓库复现完整搜索服务，也无法断言后端使用了向量检索、特定搜索引擎或某种重排算法。

依据：[技能定义](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/SKILL.md)、[Python 客户端](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/anysearch_cli.py)、[固定版本文件树](https://github.com/anysearch-ai/anysearch-skill/tree/15b7ea5039983c9dee328be8c7c609f3eb86058e)。

## 2. 能力与边界

| 能力 | 实现和用途 | 边界 |
| :--- | :--- | :--- |
| 通用搜索 | `search` 输入问题，返回标题、URL 和摘要/内容 | 单次 1–10 条；不能据此断言覆盖率或实时性 |
| 垂直搜索 | 用 `tag` 和 `params` 选择专业能力 | 实际能力和参数以远端目录为准 |
| 能力发现 | `get_sub_domains` 返回子领域名称、说明及参数要求；一次最多五个领域 | 返回能力说明，不证明结果质量 |
| 并行搜索 | `batch_search` 执行 1–5 个查询，可以混合通用和垂直查询 | 每项独立请求、独立计入额度；按输入顺序输出，单项失败不阻断其余结果 |
| 正文抽取 | `extract` 将 URL 交给服务端，客户端输出 Markdown | 声明支持 HTML/XHTML、文本、JSON、Markdown；不支持 PDF、Word、图片、音视频 |
| 跨平台调用 | Python、Node.js、PowerShell、Bash 四种 CLI | 宿主 Agent 仍需加载技能、运行命令和理解结果 |

领域常量包括 `general` 和另外 16 个领域：资源、社交媒体、金融、学术、法律、健康、商业、安全、知识产权、代码、能源、环境、农业、旅行、影视、游戏。这是领域目录，不等于全部已经验证。

本次实际查询了 `code`、`academic`、`finance` 在线目录。例如，当前 `code.doc` 要求 `library` 参数；`code.snippet` 提供语言、仓库和路径过滤参数。目录关于覆盖范围的描述未经独立验证。

正文长度也有限制：文档说明 HTML/纯文本可能在 50,000 字符处截断，过大的 JSON/Markdown 会报错。“全文抽取”受到格式和长度限制。

依据：[接口规范](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/shared/doc_spec.md)、[领域常量](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/shared/constants.json)、[验证记录](02-verification.md)。

## 3. 技术原理

### 3.1 Agent 决策与技能规范

`SKILL.md` 定义触发条件、领域选择规则、参数使用方法和运行时选择方式。推荐策略是：领域问题先查能力目录，纯百科问题直接通用搜索；不确定或跨领域时组合通用与垂直查询。

这里的“智能路由”主要由宿主大模型阅读规则后执行。客户端没有独立的意图分类模型，也没有强制验证 Agent 是否先调用过目录。结果综合、事实核对和报告写作仍需要宿主 Agent 完成。

上述描述限定在本仓库的客户端层。进一步查看官网发现，服务端还声明具备自动意图路由和跨领域重排；具体实现未公开，见[服务端补充研究](03-server-and-capabilities.md)。

### 3.2 动态发现能力，再组织参数

以“查询 React useEffect 的清理逻辑”为例：

1. Agent 查询 `code` 领域目录。
2. 服务端返回 `code.doc` 的用途和 `library` 必填要求。
3. Agent 传入 `tag=code.doc`、`params={"library":"react"}`。
4. CLI 发出请求，并将结果转为 Markdown。
5. Agent 必要时读取来源正文，整理回答。

本次观察到，静态文档的部分 `code.doc` 示例没有传 `library`，但当前目录要求它。这证明动态发现对适应参数变化有实际价值，也说明复制旧示例并不可靠。

规范要求在会话中复用已查目录，但客户端没有持久化目录缓存；复用主要依靠 Agent 上下文。

### 3.3 普通 HTTP API 适配

| 接口 | 作用 |
| :--- | :--- |
| `GET /v1/sub-domains` | 查询领域能力 |
| `POST /v1/search` | 通用或垂直搜索 |
| `POST /v1/extract` | 获取页面正文 |

接口使用 JSON，CLI 格式化为 Markdown。旧参数 `sub_domain`、`sub_domain_params` 被转换为 `tag`、`params`。密钥通过 Bearer 认证发送，也支持额度较低的匿名访问。

当前实现直接访问 REST，不需要单独安装 MCP 服务。Python 请求有 30 秒超时，但没有通用的自动退避重试、跨服务商故障切换或查询结果缓存。

### 3.4 客户端并行

批量查询拆成最多五个独立搜索请求。Python 用线程和队列，Node.js 用 `Promise.all` 收集结果，最后按输入位置整理。

它可以减少独立查询的串行等待，但不自动执行跨结果去重、全局排序、冲突裁决或报告生成。批量查询也不是只消耗一次搜索额度。

### 3.5 共享规范与跨语言维护

四种语言共享 `constants.json`、`doc_spec.md`。`generate.py` 将版本、常量和文档渲染代码同步到指定区块；业务逻辑仍分别实现。

CI 检查生成内容是否漂移，并通过本地模拟 HTTP 服务验证参数转换、异常、并发和输出顺序。适合维护轻量跨平台工具，但仍需照顾四套业务实现的一致性。

依据：[Python](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/anysearch_cli.py)、[Node.js](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/anysearch_cli.js)、[生成器](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/scripts/generate.py)、[CI](https://github.com/anysearch-ai/anysearch-skill/blob/15b7ea5039983c9dee328be8c7c609f3eb86058e/.github/workflows/ci.yml)。

## 4. 使用场景

以下是基于功能的适用性判断，并非所有场景均经过端到端验证。

| 场景 | 可以怎样用 | 需要额外补充 |
| :--- | :--- | :--- |
| 编程助手 | 检索框架文档、代码片段，读取来源后解释或生成代码 | 版本约束、示例执行与正确性检查 |
| 技术/竞品调研 | 并行搜关键词和领域，再读取重点页面 | 去重、证据整理、报告生成与覆盖率评估 |
| 学术资料收集 | 查询论文、学术或生物医学文献目录 | PDF 解析、全文阅读与引文核验 |
| 行业信息助手 | 使用金融、商业等目录能力 | 专业规则、数据时间和来源核验 |
| 事实核查 | 检索多个来源，由 Agent 对照主张 | 来源独立性、证据等级与冲突判断 |
| 信息监测 | 外部调度器定期执行搜索，比较新旧结果 | 调度、历史存储、差异检测与通知 |

它适合“已有 Agent，需要统一检索入口”的情况。离线搜索、大规模站点采集、登录态网页操作、多媒体解析和完整企业知识库都超出当前仓库实现。

## 5. 可扩展方向

以下是建议，不是上游已实现功能。

| 优先级 | 方向 | 做法与收益 |
| :--- | :--- | :--- |
| 高 | 质量评测 | 建分领域题集，对比通用/垂直/混合策略，记录准确率、来源覆盖、时效、延迟和成本，验证“垂直更好”的主张 |
| 高 | 稳定性 | 对 429 和临时故障做受限退避重试，加入额度预算、失败分类与可观测日志 |
| 高 | JSON 输出 | 保留结构化元数据、逐项状态和来源信息，方便工作流与数据库集成 |
| 高 | 目录缓存与参数校验 | 缓存设置过期时间，按远端 schema 校验参数；目录变化或校验失败时刷新 |
| 中 | 研究工作流 | 增加问题拆解、去重、重排、证据摘录、交叉核验和带来源报告 |
| 中 | 多服务商接入 | 通过兼容网关接其他搜索服务或私有知识库，按领域、价格、可用性路由 |
| 中 | 企业知识检索 | 连接内部文档和工单，增加权限过滤、增量索引和公私来源区分 |
| 中 | 文档/浏览器处理 | 为 PDF/OCR、动态页面和登录态内容单独连接处理器 |
| 中 | 行业工作台 | 加历史存储、变化检测和报告模板，形成技术雷达、论文跟踪器等 |

客户端已有 `ANYSEARCH_API_BASE_URL` 覆盖点，可作为兼容网关的入口。但换地址不等于拥有检索后端，多服务商和私有化仍需另做服务实现。

## 6. 研究判断

最值得借鉴的是“能力发现 → 领域选择 → 参数化调用 → 并行取证 → 正文读取”的集成方式，以及多运行时共享规范的维护设计。

当前证据支持客户端功能和少量匿名在线接口可用。它不支持“全部领域稳定可用”“垂直一定优于通用”“数据一定实时”或“完整服务可私有化”等更强结论。本次检查范围内没有足以验证这些结论的质量基准或搜索后端源码。

后续补充：官网存在自报评测，但本研究未复现，不能替代独立验证；详细范围见[服务端补充研究](03-server-and-capabilities.md)。
